תרגיל 1 - חימום מעשי

התרגילים האלה מתרגלים כל אחד מהנושאים שלמדנו בבוקר, בתוך Cursor. הם קצרים בכוונה - המטרה היא לצבור ביטחון בעבודה עם agent, לא לבנות מוצר.

איך עובדים

  1. פתחו את Cursor בתיקיית סביבת ההדרכה.
  2. פתחו את חלונית ה-Chat/Agent (ברירת מחדל: Ctrl+I / Cmd+I).
  3. ודאו שאתם במצב Agent (ולא Chat/Ask בלבד).
  4. בצעו את התרגילים לפי הסדר. לכל תרגיל: מטרה, שלבים, ו"מה למדנו".

זכרו את הכלל מהחלק העיוני: Context זה הכל. ככל שתסבירו טוב יותר מה אתם רוצים ותצרפו את הקבצים הרלוונטיים - כך התוצאה תהיה טובה יותר. וגם: אתם ה-Reviewer - תמיד קראו את מה שה-agent הציע לפני שאתם מאשרים.

תרגיל 1 נושא: עבודה עם agent, prompt טוב, קריאת הפלט.

תרגיל 1 - עבודה ראשונה עם Agent

מטרה

להתרגל לפתוח שיחה, לנסח בקשה ברורה, ולקרוא בביקורתיות את מה שה-agent מחזיר.

שלבים

  1. פתחו את חלונית ה-Agent ב-Cursor וודאו שאתם במצב Agent.
  2. בקשו מה-agent ליצור קובץ חדש playground/greeting.js עם פונקציה שמחזירה ברכת בוקר טוב בעברית לפי השעה הנוכחית.
    • נסחו זאת בבירור: מה הקלט, מה הפלט, איפה הקובץ.
  3. קראו את הקוד שה-agent יצר. שאלו את עצמכם: האם הוא עושה בדיוק מה שביקשתי?
  4. בקשו שינוי קטן: "הוסף גם ברכת ערב טוב אחרי השעה 18:00".
  5. שימו לב איך ה-agent מוצא את הקובץ הקודם ומעדכן אותו (Context + Tools).
נסו גם
  • שאלו את ה-agent שאלה תיאורטית: "הסבר לי בקצרה מה זה closure ב-JavaScript". שימו לב להבדל בין שאלת ידע (Chat) לבין בקשת פעולה (Agent).
  • נסחו את אותה בקשה פעם אחת במעורפל ("תעשה משהו עם ברכות") ופעם אחת בצורה מדויקת. השוו את התוצאות.
תרגיל 2 נושא: שימוש ב-agent כדי להבין קוד לא מוכר.

תרגיל 2 - הבנת Codebase

מטרה

לגלות כמה מהר אפשר להבין קוד חדש כשמבקשים מה-agent להסביר - במקום לקרוא הכל לבד.

שלבים

  1. פתחו את הקובץ sample-code/finance-utils.js (אל תקראו אותו לעומק עדיין).
  2. בקשו מה-agent: "הסבר לי מה הקובץ finance-utils.js עושה, פונקציה-פונקציה, בעברית פשוטה."
  3. שאלו שאלת המשך ממוקדת: "איזו מהפונקציות הכי מסוכנת לשימוש ולמה?"
  4. בקשו דוגמת שימוש: "תן לי דוגמת קוד שמשתמשת ב-transactionsAbove על רשימה של 3 תנועות."
  5. בקשו סקירת מבנה: "אם היו כאן עוד 20 קבצים, איך היית ממליץ לי להתחיל להבין את הפרויקט?"
נסו גם
  • בקשו מה-agent לצייר את זרימת הנתונים בטקסט או ב-diagram.
  • שאלו: "האם יש כאן קוד שנראה לך חשוד או לא נכון?" (רמז: יש. נתקן אותו בתרגיל 4.)
מה למדנו
  • ה-agent הוא כלי לימוד מצוין ל-codebase לא מוכר.
  • שאלות ממוקדות מקבלות תשובות טובות יותר.
  • זהו בדיוק הכישור שנשתמש בו בתרגיל 2 על אפליקציה אמיתית.
תרגיל 3 נושא: פיתוח קוד חדש עם agent, בצעדים.

תרגיל 3 - פיתוח פיצ'ר קטן

מטרה

לפתח פונקציונליות חדשה קטנה מקצה לקצה, תוך עבודה בצעדים ובדיקה תוך כדי.

המשימה

נוסיף לקובץ sample-code/finance-utils.js פונקציה חדשה:

compoundInterest(principal, annualRate, years) - שמחשבת ריבית דריבית (compound) ומחזירה את הסכום הסופי (קרן + ריבית).

שלבים

  1. בקשו מה-agent להוסיף את הפונקציה, כולל תיעוד (JSDoc) בסגנון הפונקציות הקיימות.
  2. בקשו שגם יעדכן את module.exports בהתאם.
  3. בקשו דוגמת הרצה קטנה שמדפיסה את התוצאה עבור: קרן 10000, ריבית 5%, 3 שנים.
  4. הריצו את הדוגמה (בקשו מה-agent להריץ אותה בטרמינל) וודאו שהתוצאה הגיונית (~11576).
  5. בקשו מה-agent להסביר בשורה אחת מה ההבדל בין הפונקציה הזו ל-simpleInterest.
נסו גם
  • בקשו שיתמוך גם בתדירות היוון (חודשי/שנתי) כפרמטר אופציונלי.
  • שימו לב: ככל שהבקשה מדויקת יותר (חתימה, שם, סגנון) - כך התוצאה קרובה יותר לרצוי.
מה למדנו
  • עבודה בצעדים קטנים + אימות בהרצה = פחות הפתעות.
  • בקשה לעקוב אחרי סגנון הקוד הקיים שומרת על אחידות.
תרגיל 4 נושא: שימוש ב-agent לאיתור ותיקון באג.

תרגיל 4 - מציאה ותיקון באג

מטרה

לתרגל את הלולאה: לשחזר בעיה → למצוא סיבה → לתקן → לאמת.

הרקע

בקובץ sample-code/finance-utils.js יש פונקציה average שאמורה להחזיר ממוצע של רשימת סכומים - אבל היא מחזירה תוצאה שגויה.

שלבים

  1. בקשו מה-agent להריץ את הפונקציה על הקלט [100, 200, 300] ולהגיד מה היא מחזירה.
    • התוצאה הצפויה: 200. מה מתקבל בפועל?
  2. בקשו: "מצא את הבאג בפונקציה average והסבר לי אותו לפני שאתה מתקן."
  3. קראו את ההסבר. האם הוא הגיוני? (רמז: שימו לב לתנאי הלולאה.)
  4. אשרו את התיקון, ובקשו מה-agent להריץ שוב ולאמת שהתוצאה נכונה.
  5. בקשו: "האם יש עוד קלטים שעלולים לשבור את הפונקציה הזו?" (למשל רשימה ריקה.)
נסו גם
  • בקשו מה-agent להוסיף בדיקת קלט לרשימה ריקה.
  • שימו לב איך הרצת הקוד (Tool) הפכה "אני חושב שזה הבאג" ל"בדקתי, זה הבאג".
מה למדנו
  • אימות מול המציאות (הרצה) הוא המפתח לתיקון באגים אמין.
  • כדאי לבקש הסבר לפני התיקון - כדי לוודא שה-agent הבין נכון.
תרגיל 5 נושא: שימוש ב-agent ל-review ולכתיבת טסטים.

תרגיל 5 - Review וכתיבת טסטים

מטרה

להשתמש ב-agent גם ככלי בקרת איכות: לבקר קוד ולכסות אותו בטסטים.

חלק א' - Review

  1. בקשו מה-agent: "עשה code review לקובץ finance-utils.js. ציין בעיות אפשריות, edge cases, ושיפורים - אבל אל תשנה כלום עדיין."
  2. קראו את ההערות. עם מה אתם מסכימים? עם מה לא?
  3. בחרו הערה אחת שאתם מסכימים איתה ובקשו ליישם רק אותה.

חלק ב' - טסטים

  1. בקשו מה-agent לכתוב טסטים לפונקציות ב-finance-utils.js (אפשר עם node:test המובנה, ללא התקנות).
  2. בקשו שהטסטים יכללו גם מקרי קצה: רשימה ריקה, מספרים שליליים, ריבית 0.
  3. בקשו מה-agent להריץ את הטסטים ולדווח מה עובר ומה נכשל.
  4. אם משהו נכשל - החליטו יחד עם ה-agent: האם זה באג בקוד או בטסט?
נסו גם
  • בקשו כיסוי טסטים לפונקציה compoundInterest שהוספתם בתרגיל 3.
מה למדנו
  • Review מ-agent הוא נקודת מבט נוספת - לא תחליף לשיפוט שלכם.
  • טסטים הופכים "נראה תקין" ל"מוכח שתקין", והם רשת ביטחון לשינויים עתידיים.
תרגיל 6 נושא: הגדרת חוקים קבועים ל-agent.

תרגיל 6 - התאמה אישית של Agent (Rules)

מטרה

ללמוד להגדיר פעם אחת את הסטנדרטים של הצוות, כך שה-agent יעבוד לפיהם אוטומטית.

רקע

במקום לחזור על אותן הנחיות בכל שיחה ("כתוב בעברית", "השתמש ב-async/await", "אל תשתמש בספרייה X"), אפשר להגדיר Rules שה-agent מקבל תמיד: קבצים בתיקייה .cursor/rules/.

שלבים

  1. בקשו מה-agent ליצור כלל חדש .cursor/rules/my-team.mdc עם הכללים הבאים (התאימו לטעמכם):
    • קוד JavaScript מודרני (ES modules / async-await).
    • שמות משתנים ופונקציות באנגלית, הערות בעברית.
    • כל פונקציה חדשה מתועדת ב-JSDoc.
    • אין להוסיף ספריות חיצוניות בלי אישור.
  2. פתחו שיחה חדשה ובקשו משימת קוד קטנה (למשל: פונקציה שממירה דולר לשקל).
  3. בדקו: האם ה-agent פעל לפי הכללים שהגדרתם? (הערות בעברית? JSDoc?)
  4. שנו כלל אחד ב-.cursor/rules/ ובקשו משימה נוספת - ראו שההתנהגות משתנה.
נסו גם
  • הוסיפו כלל ספציפי לדומיין: "כל סכום כספי מוצג עם 2 ספרות אחרי הנקודה ובמטבע ILS".
  • דונו: אילו כללים היו עוזרים לצוות שלכם בעבודה האמיתית?
מה למדנו
  • Rules (.cursor/rules/) + AGENTS.md = הדרך לגרום ל-agent לעבוד לפי הסטנדרטים שלכם.
  • זה חוסך חזרות ומבטיח אחידות - נשתמש בזה בתרגיל 2.
תרגיל 7 נושא: תרגיל משולב שמפעיל את כל מה שלמדנו.

תרגיל 7 - לחבר הכל

מטרה

לבצע משימה קטנה מקצה לקצה, ולהפעיל את כל הכישורים: הבנה, פיתוח, תיקון, טסטים והתאמה אישית.

המשימה

בנו מודול קטן חדש sample-code/loan.js שמנהל חישובי הלוואה פשוטים:

  1. הבנה + תכנון: בקשו מה-agent להציע תכנית קצרה למודול שכולל:
    • monthlyPayment(principal, annualRate, months) - תשלום חודשי.
    • totalRepayment(principal, annualRate, months) - סך החזר כולל.
    • remainingBalance(principal, annualRate, months, paymentsMade) - יתרה לאחר X תשלומים.
  2. פיתוח: אשרו את התכנית ובקשו מימוש, לפי הכללים מ-AGENTS.md (תרגיל 6).
  3. בדיקה: בקשו דוגמת הרצה ואמתו שהמספרים הגיוניים.
  4. טסטים: בקשו טסטים למודול, כולל edge cases.
  5. Review: בקשו מה-agent לבקר את הקוד שלו-עצמו ולתקן בעיה אחת לפחות.
  6. תיעוד: בקשו הוספת סעיף קצר ל-README קטן שמסביר איך להשתמש במודול.

דיון מסכם (בקבוצה)

  • באילו שלבים ה-agent חסך לכם הכי הרבה זמן?
  • איפה נאלצתם להתערב או לתקן אותו?
  • מה תיקחו איתכם לתרגיל 2?
מה למדנו
  • זרימת עבודה מלאה עם agent: תכנון → פיתוח → אימות → טסטים → review.
  • זה בדיוק המבנה של תרגיל 2, רק על אפליקציה אמיתית וגדולה יותר.

חקירת אפליקציה אמיתית עם Agents

תרגיל 2 - חקירת אפליקציה אמיתית עם Agents

היום ניקח אפליקציה שלמה (FinDash), נחקור אותה, נתקן בה באגים ונפתח בה פיצ'ר - הכל דרך agents ב-Cursor. המטרה: לחוות זרימת עבודה אמיתית מקצה לקצה, בדיוק כמו בעבודה היומיומית.

כלל הזהב

כל פעולה נעשית דרך ה-agent ב-Cursor. לא כותבים קוד ידנית, לא מריצים פקודות ידנית בטרמינל שמחוץ ל-Cursor. אתם המנהלים - ה-agent הוא המפתח. אתם מגדירים מטרה, נותנים Context, קוראים ומאשרים.

טיפים כלליים (מתרגיל 1)

  • Context זה הכל - צרפו קבצים רלוונטיים, הצביעו על מיקומים ספציפיים.
  • תנו ל-agent לאמת - שיריץ את השרת/הטסטים, לא רק "יטען".
  • אתם ה-Reviewer - קראו כל diff לפני שמאשרים.
  • עבדו בצעדים - משימה גדולה = כמה צעדים קטנים עם בדיקות ביניים.

שלב 0

שלב 0 - הכנה

מטרה

לוודא שהסביבה מוכנה לפני שמתחילים לעבוד עם ה-agent.

מה צריך

  1. Cursor מותקן ופתוח.
  2. Node.js מותקן (גרסה 18 ומעלה). בדקו: פתחו טרמינל ב-Cursor והריצו node --version.
  3. Git מותקן ומוגדר עם שם ואימייל.
  4. גישה ל-GitHub - repo של FinDash: https://github.com/maorbarak100-creator/findash. בשלב 1 תגדירו גם GitHub MCP (נדרש PAT).
  5. גישה ל-Azure DevOps - קישור ל-Board/Work Item שהמדריך יצר. בשלב 5 תגדירו Azure DevOps MCP (שם ארגון + הרשאות).

בדיקת מוכנות

  • פתחו את חלונית ה-Agent (ברירת מחדל: Ctrl+I).
  • ודאו שהמצב הוא Agent (ולא Ask/Chat בלבד).
  • בחרו תיקייה ריקה שתשמש לעבודה היום (למשל C:\work\findash).
  • הכינו מראש: אפשרות ליצור GitHub PAT, וגישה לארגון ADO שהמדריך יציין.

תזכורת חשובה

מהרגע הזה - כל דבר עובר דרך ה-agent. גם פקודות git, גם הרצת השרת, גם עריכת קוד. בשלבים 1 ו-5 תוסיפו גם כלים חיצוניים דרך MCP.

שלב 1

שלב 1 - משיכת ה-Repo מ-GitHub (עם Agent)

מטרה

להביא את קוד האפליקציה מ-GitHub למחשב - באמצעות ה-agent, בלי להריץ פקודות ידנית. קודם מחברים את GitHub MCP, אחר כך משכפלים.

MCP Setup

הכנת MCP: GitHub

MCP מחבר את Cursor ל-GitHub ככלי חיצוני (אותה לולאת tool calling, מעבר לכלים המובנים). בלי זה ה-agent רואה בעיקר את הקבצים המקומיים.

  1. צרו Personal Access Token (PAT) ב-GitHub: https://github.com/settings/tokens (Classic: scope מינימלי repo / גישה לקריאה ל-repos. אל תשתפו את הטוקן עם אף אחד.)
  2. ב-Cursor: Settings → Tools & MCP → New MCP Server (או ערכו את הקובץ הגלובלי %USERPROFILE%\.cursor\mcp.json ב-Windows / ~/.cursor/mcp.json ב-Mac/Linux).
  3. הוסיפו (או המיזגו) את ההגדרה הבאה. החליפו את YOUR_GITHUB_PAT בטוקן האמיתי שלכם:
{
  "mcpServers": {
    "github": {
      "url": "https://api.githubcopilot.com/mcp/",
      "headers": {
        "Authorization": "Bearer YOUR_GITHUB_PAT"
      }
    }
  }
}
  1. שמרו את הקובץ, ואז Restart ל-Cursor (או Developer: Reload Window).
  2. ודאו ב-Settings → Tools & MCP שיש נקודה ירוקה ליד github.
  3. בדיקת עשן בחלונית Agent:

    "האם כלי GitHub MCP זמינים? תאר לי בקצרה את ה-repo maorbarak100-creator/findash."

אבטחה: אל תדביקו PAT ב-chat, ב-commit, או ב-repo של ההדרכה. רק בקונפיג המקומי של Cursor.

שלבים (Clone + Setup)

  1. פתחו את חלונית ה-Agent (מצב Agent).
  2. בקשו מה-agent לאמת הקשר מ-GitHub ואז לשכפל:

    "בעזרת GitHub MCP אמת שה-repo maorbarak100-creator/findash קיים, אחר כך שכפל (clone) אותו מהכתובת https://github.com/maorbarak100-creator/findash לתיקייה הנוכחית, ופתח אותה."

  3. תנו ל-agent להריץ את git clone בטרמינל. שימו לב לדיווח על ההצלחה.
  4. בקשו מה-agent להתקין את התלויות:

    "התקן את התלויות של ה-backend ושל ה-frontend."

  5. בקשו להריץ את שני החלקים ולוודא שהם עולים:

    "הרץ את ה-backend ואת ה-frontend, ואמת שהאפליקציה עובדת. תן לי את הכתובת לפתיחה בדפדפן."

  6. פתחו בדפדפן את http://localhost:4200 - אתם אמורים לראות את רשימת החשבונות.

נקודות לתשומת לב

  • אם ה-MCP לא עולה (חומה / מדיניות ארגון): המשיכו עם clone דרך הטרמינל בלבד, והשלימו את שאר השלב. תעדו לעצמכם מה חסם את ה-MCP.
  • אם ה-clone נכשל: בדקו את הכתובת ואת ההרשאות ב-GitHub.
  • שימו לב שה-agent מזהה שיש שתי תיקיות (backend, frontend) וכל אחת דורשת npm install נפרד. אם לא - הזכירו לו.
מה למדנו
  • MCP מרחיב את לולאת ה-tools מעבר לכלים המובנים של ה-harness (כאן: GitHub).
  • ה-agent יכול לנהל פעולות git ותפעול (setup) - לא רק לכתוב קוד.
  • כבר בשלב הזה אנחנו נותנים לו לאמת שהאפליקציה עובדת (Tool calling).

עברו ל-שלב 2 - ארכיטקטורה.

שלב 2

שלב 2 - חקירת האפליקציה ולימוד הארכיטקטורה

מטרה

להבין codebase חדש במהירות, בעזרת ה-agent - בדיוק כמו כשמצטרפים לפרויקט חדש בעבודה.

שלבים

א. תמונה כללית

בקשו מה-agent:

"תן לי סקירה כללית של הפרויקט הזה: מה האפליקציה עושה, מאילו חלקים היא מורכבת, ובאילו טכנולוגיות היא משתמשת."

ב. מפת ארכיטקטורה

"צייר לי דיאגרמת ארכיטקטורה (ב-HTML) שמראה איך ה-frontend, ה-backend והנתונים מתחברים."

ג. זרימת נתונים ספציפית

בחרו תרחיש והבינו אותו מקצה לקצה:

"כשמשתמש פותח מסך של חשבון ורואה את היתרה - עקוב אחרי כל הזרימה: מאיזה קומפוננטה זה מתחיל, איזה קריאת API נעשית, ואיפה בשרת מחושבת היתרה?"

ד. מיפוי ה-API

"רשום לי טבלה של כל ה-endpoints ב-backend: method, נתיב, ומה כל אחד מחזיר."

ה. שאלות משלכם

שאלו לפחות שתי שאלות משלכם, למשל:

  • "איפה מאוחסנים הנתונים ואיך הם נטענים?"
  • "מה יקרה אם אבקש חשבון שלא קיים?"
  • "איזה קוד היית משפר קודם כל, ולמה?"

משימת סיכום

בקשו מה-agent:

"צור קובץ ARCHITECTURE.md קצר שמסכם את מבנה הפרויקט, ה-endpoints וזרימת הנתונים המרכזית."

קראו את הקובץ שנוצר - האם הוא מדויק? תקנו עם ה-agent מה שלא נכון.

מה למדנו
  • ה-agent הופך codebase לא מוכר לנגיש תוך דקות.
  • שאלות ממוקדות + בקשת דיאגרמות = הבנה מהירה.
  • תיעוד שנוצר תוך כדי חקירה נשאר נכס לצוות.

עברו ל-שלב 3 - תיקון באג.

שלב 3

שלב 3 - מציאה ותיקון של באג

הרקע (דיווח באג)

דיווח מלקוח: "היתרה שמוצגת בחשבון שלי נראית גבוהה מדי. יש לי הרבה משיכות, אבל היתרה רק גדלה. משהו לא הגיוני בחישוב."

המשימה שלכם: לשחזר, לאתר, לתקן ולאמת - הכל עם ה-agent.

שלבים

א. שחזור הבעיה

"בדוק את היתרה של חשבון acc-1001 מול התנועות שלו. חשב ידנית מה היתרה אמורה להיות והשווה למה שה-API מחזיר. האם יש פער?"

תנו ל-agent להריץ את השרת ולבצע קריאה אמיתית ל-endpoint של היתרה.

ב. איתור שורש הבעיה

"מצא את הקוד שמחשב את היתרה, קרא אותו, והסבר לי מה הבאג - לפני שאתה מתקן."

עצרו וקראו את ההסבר. האם הוא הגיוני? (רמז: חשבו על ההבדל בין הפקדה למשיכה.)

ג. תיקון

"תקן את הבאג. שמור על סגנון הקוד הקיים."

קראו את ה-diff לפני שאתם מאשרים. ודאו שאתם מבינים כל שינוי.

ד. אימות

"הרץ שוב את חישוב היתרה עבור שלושת החשבונות ואמת שהתוצאות נכונות עכשיו."

בדקו גם בממשק (רעננו את מסך החשבון) שהיתרה השתנתה והגיונית.

ה. רשת ביטחון

"כתוב טסט ל-backend שמאמת את חישוב היתרה, כדי שהבאג הזה לא יחזור. הרץ את הטסטים."

משימת סגירה (Git)

"צור branch בשם fix/balance-calculation, בצע commit עם הודעה ברורה בעברית שמתארת את התיקון, ודחוף אותו."

מה למדנו
  • הלולאה המלאה: שחזור → איתור → תיקון → אימות → טסט.
  • אימות מול המציאות (הרצה) הוא ההבדל בין "אני חושב שתיקנתי" ל"בדקתי, תיקנתי".
  • הוספת טסט הופכת את התיקון לקבוע.

עברו ל-שלב 4 - באג Cache.

שלב 4

שלב 4 - באג שדורש לוגים והרצה (Cache)

הרקע (דיווח באג)

דיווח מלקוח: "הוספתי הפקדה לחשבון. רשימת התנועות התעדכנה מיד, אבל היתרה נשארה כמו קודם. רק אחרי שאני מפעיל מחדש את השרת היתרה מתעדכנת. משהו לא תקין."

זה באג אחר משלב 3. חישוב היתרה על נתוני ה-seed כבר אמור להיות תקין אחרי התיקון הקודם. כאן הבעיה מופיעה רק אחרי כתיבה ואז קריאה באותו תהליך שרת (בלי restart).

כלל לשלב הזה: אל תתקנו עדיין. קודם תשחזרו, תוסיפו לוגים, ותסבירו את ה-root cause מתוך הראיות.

שלבים

א. שחזור הבעיה (בלי תיקון)

"בלי לשנות קוד עדיין: קרא את יתרת acc-1001 (GET balance), אחר כך הוסף הפקדה של 500 דרך POST /api/accounts/acc-1001/transactions, ואז קרא שוב balance וגם transactions. השווה: האם היתרה עלתה? האם transactionCount תואם לאורך רשימת התנועות? חשוב: אל תפעיל מחדש את השרת בין הבדיקות."

תנו ל-agent להריץ את הרצף בפועל (curl / fetch מול השרת שכבר רץ).

ב. Instrumentation - הוספת לוגים

"עדיין בלי לתקן. הוסף loglines זמניים שמראים: האם חזרה תשובה מ-cache או מחישוב חדש, את ערך ה-balance, את transactionCount, ואת מספר התנועות ברשימה. שחזר את אותו רצף (GET → POST → GET) והצג לי את הלוגים."

קראו את הלוגים יחד עם ה-agent. מה הראיות אומרות?

ג. הסבר לפני תיקון

"מה ה-root cause לפי הלוגים? הסבר לי לפני שאתה מתקן."

עצרו וקראו את ההסבר. האם הוא מתבסס על הראיות (cache hit אחרי POST, txnCount ישן מול רשימה חדשה) ולא רק על ניחוש מקריאת הקוד?

ד. תיקון

"תקן כך שאחרי הוספת תנועה היתרה תתעדכן בלי restart. שמור על סגנון הקוד הקיים. אחרי התיקון הסר את הלוגים הזמניים."

קראו את ה-diff לפני אישור. ודאו שהתיקון הוא invalidation (או עדכון) של ה-cache בנתיב הכתיבה, ולא שינוי מחדש של נוסחת החישוב משלב 3.

ה. אימות

"בלי להפעיל מחדש את השרת: הוסף שוב הפקדה, קרא balance ו-transactions, ואמת שהיתרה ו-transactionCount מעודכנים."

ו. רשת ביטחון

"כתוב טסט ל-backend שמוסיף תנועה לחשבון ואז בודק שהיתרה משקפת את התנועה החדשה (בלי להניח restart). הרץ את הטסטים."

משימת סגירה (Git)

"צור branch בשם fix/balance-cache-invalidation, בצע commit עם הודעה ברורה בעברית שמתארת את התיקון, ודחוף אותו."

מה למדנו
  • קריאת קוד נותנת השערות. לוגים + הרצה נותנים ראיות.
  • באגים מסוג cache / stale state נראים "תקינים" ב-static analysis, ונחשפים רק ברצף write-then-read.
  • ה-agent חזק כשהוא סוגר לולאה מול המערכת הרצה, לא כשהוא רק מנחש מהקוד.

עברו ל-שלב 5 - Work Item.

שלב 5

שלב 5 - משיכת ה-Work Item מ-Azure DevOps

מטרה

לקבל את דרישת הפיצ'ר ממערכת ניהול המשימות (Azure DevOps) דרך MCP, ואז לתרגם אותה לתוכנית עבודה עם ה-agent, בלי לכתוב קוד עדיין.

MCP Setup

הכנת MCP: Azure DevOps

כאן מחברים את Cursor ל-Azure DevOps כדי שה-agent יוכל למשוך Work Items ישירות (במקום להעתיק ידנית מהדפדפן).

  1. בקשו מהמדריך את שם הארגון ב-ADO (YOUR_ADO_ORG) ואת מזהה / קישור ה-Work Item לתרגיל.
  2. ודאו שיש לכם גישה לארגון (דפדפן נפתח ל-dev.azure.com). לפי מדיניות הארגון: התחברות עם Microsoft Entra, או az login, או PAT ל-ADO.
  3. ב-Cursor: Settings → Tools & MCP → New MCP Server, או צרו/ערכו .cursor/mcp.json ב-workspace (או בקובץ הגלובלי %USERPROFILE%\.cursor\mcp.json).
  4. הוסיפו את ההגדרה הבאה. החליפו את YOUR_ADO_ORG בשם הארגון האמיתי:
{
  "mcpServers": {
    "ado": {
      "command": "npx",
      "args": ["-y", "@azure-devops/mcp", "YOUR_ADO_ORG"]
    }
  }
}
  1. שמרו, ואז Restart / Reload ל-Cursor. אשרו Enable כש-Cursor מזהה את השרת.
  2. ודאו נקודה ירוקה ליד ado ב-Tools & MCP.
  3. בדיקת עשן:

    "האם כלי Azure DevOps MCP זמינים? רשום לי בקצרה מה אתה יכול לעשות מול Work Items."

אבטחה: אל תשמרו PAT של ADO בתוך repo משותף. אם הארגון דורש PAT, השתמשו במשתנה סביבה מקומי לפי הנחיות המדריך, לא בקובץ שמתועד ל-git.

שלבים

א. משיכת ה-Work Item דרך MCP

  1. קחו מהמדריך את מזהה ה-Work Item (או את הכותרת המדויקת): "הוספת סיכום חודשי של הכנסות מול הוצאות למסך החשבון".
  2. בקשו מה-agent:

    "משוך מ-Azure DevOps (דרך MCP) את ה-Work Item של הסיכום החודשי. הצג לי את התיאור ואת תנאי הקבלה (Acceptance Criteria), ואז הצע תוכנית מימוש קצרה: מה ב-backend, מה ב-frontend, ובאיזה סדר. אל תכתוב קוד עדיין."

ב. Fallback (אם MCP חסום)

אם ה-MCP לא עובד בסביבה הארגונית: פתחו את הלוח בדפדפן, העתיקו ידנית את התיאור ואת Acceptance Criteria, והדביקו ל-agent עם אותה בקשה לתוכנית (בלי קוד).

ג. אישור התוכנית

קראו את התוכנית שה-agent הציע. האם היא מכסה את כל תנאי הקבלה? חדדו אם צריך:

"ודא שהתוכנית מכסה גם את המקרה של חשבון ללא תנועות ואת החזרת 404 לחשבון לא קיים."

מה למדנו
  • MCP ל-ADO מחליף copy-paste: הדרישה נכנסת ל-context ישירות מהמערכת הארגונית.
  • דרישה טובה (עם Acceptance Criteria) = Context מצוין ל-agent.
  • לבקש תוכנית לפני קוד = שליטה טובה יותר בתוצאה.

עברו ל-שלב 6 - מימוש פיצ'ר.

שלב 6

שלב 6 - מימוש הפיצ'ר

מטרה

לממש את פיצ'ר "הסיכום החודשי" מקצה לקצה (backend + frontend), לפי תנאי הקבלה, עם ה-agent.

תזכורת לתנאי הקבלה (מה-Work Item):

  • endpoint חדש GET /api/accounts/:id/summary שמחזיר לכל חודש: month, income, expense.
  • מסודר מהחודש המוקדם לחדש; 404 לחשבון לא קיים; טיפול בחשבון ללא תנועות.
  • הצגה ויזואלית במסך החשבון + טסט ל-backend.

שלבים מומלצים (בצעדים!)

א. Backend - הלוגיקה

"ממש את חישוב הסיכום החודשי ב-backend: פונקציה שמקבצת תנועות לפי חודש (YYYY-MM) ומסכמת income (הפקדות) ו-expense (משיכות)."

ב. Backend - ה-Endpoint

"הוסף route GET /api/accounts/:id/summary שמשתמש בפונקציה, כולל 404 לחשבון לא קיים."

אמתו:

"הרץ את השרת ובצע קריאה ל-endpoint עבור acc-1001. הראה לי את הפלט."

(פלט צפוי: 3 חודשים - ינואר/פברואר/מרץ 2026 - עם income והוצאות לכל חודש.)

ג. Backend - טסט

"כתוב טסט שמאמת את חישוב הסיכום עבור חשבון לדוגמה, והרץ אותו."

ד. Frontend - שירות

"הוסף ל-api.service מתודה getSummary, והוסף את הטיפוסים המתאימים."

ה. Frontend - תצוגה

"הצג במסך פרטי החשבון בלוק 'סיכום חודשי' עם תרשים עמודות פשוט (הכנסות מול הוצאות לכל חודש). אל תוסיף ספריות חיצוניות - השתמש ב-CSS."

אמתו:

"הרץ את ה-frontend ואת ה-backend, ותאר לי מה אמור להופיע במסך של acc-1001."

פתחו בדפדפן וודאו שהבלוק מופיע ונכון.

ו. מקרי קצה

"בדוק מה קורה בחשבון ללא תנועות ובחשבון לא קיים. ודא שאין שגיאה בממשק."

סגירה (Git + PR)

"צור branch feature/monthly-summary, בצע commit עם הודעה ברורה, דחוף, ופתח Pull Request (אם מוגדר בארגון). קשר אותו ל-Work Item אם אפשר."

Review עצמי

"עשה code review לשינויים שביצעת בפיצ'ר הזה, וציין אם משהו חסר ביחס לתנאי הקבלה."

מה למדנו
  • מימוש פיצ'ר מלא (backend + frontend + טסט) בעבודה מונחית-agent.
  • עבודה בצעדים עם אימות בכל שלב מפחיתה הפתעות.
  • סגירת המעגל: מ-Work Item ועד Pull Request.

מי שסיים - עברו לחצי השני: שלב 7 - שיפור יומיומי.

שלב 7

שלב 7 (חצי שני) - שפר משימה יומיומית שלך

מטרה

לקחת את מה שלמדנו ולהפעיל אותו על הבעיות האמיתיות שלכם. כל אחד בוחר משימה או תהליך שחוזר על עצמו בעבודה היומיומית, ומשפר אותו בעזרת agent.

זהו הבסיס להצגה למנהלים בהמשך התוכנית.

שלב א' - בחירת משימה

חשבו על משהו מהעבודה שלכם שהוא: חוזר, מייגע, גוזל זמן, או מועד לטעויות. דוגמאות:

  • כתיבת בדיקות ליחידות קוד קיימות.
  • יצירת תיעוד ל-API / למודול.
  • כתיבת סקריפט שחוזר על עצמו (למשל עיבוד קובץ, המרת פורמט).
  • ניסוח הודעות commit / תיאורי Pull Request.
  • חקירת לוגים או שגיאות.
  • כתיבת boilerplate לקומפוננטה/מודול חדש.
  • הכנת שאילתות או דוחות.

אם אתם מתקשים לבחור - שאלו את ה-agent: "אני עובד/ת כ... והמשימות היומיומיות שלי הן... איזו מהן הכי כדאי לשפר עם AI ולמה?"

שלב ב' - הגדרת "לפני"

תעדו את המצב הנוכחי: כמה זמן זה לוקח היום? מה מייגע בזה? כתבו 2-3 שורות. זה ה"לפני" שתציגו מול ה"אחרי".

שלב ג' - שיפור עם Agent

בנו פתרון. אפשרויות:

  • אוטומציה: בקשו מה-agent לכתוב סקריפט/כלי שמבצע את המשימה.
  • Rules / AGENTS.md: הגדירו כללים שיחסכו לכם חזרה על הנחיות (כמו בתרגיל 6 בתרגיל 1).
  • Prompt חוזר: נסחו prompt-תבנית שתשמש אתכם שוב ושוב למשימה הזו.
  • תהליך: הגדירו זרימת עבודה חדשה עם ה-agent שמקצרת את המשימה.

עבדו בצעדים, אמתו, ושמרו את התוצר.

שלב ד' - מדידת "אחרי"

  • כמה זמן זה לוקח עכשיו?
  • מה השתפר באיכות / בעקביות?
  • מה עוד אפשר לשפר בהמשך?

שלב ה' - הכנה להצגה למנהלים

הכינו נקודות קצרות להצגה למנהלים:

  • מה המשימה שבחרתם ולמה.
  • ה"לפני" מול ה"אחרי" (עם מספרים אם אפשר).
  • דמו קצר של השיפור.
  • מה תיקחו קדימה.
מה למדנו
  • הערך האמיתי של agents הוא בשילוב בעבודה היומיומית, לא רק בתרגילים.
  • שיפור קטן שחוזר על עצמו כל יום = חיסכון עצום לאורך זמן.
