שני תרגילים באותו יום: מתסריטי בדיקה מתוך אפיון, ועד מייל סטטוס חי מ-Azure DevOps לטיוטה ב-Outlook. ה-agent מאיץ. אתם ה-Reviewer.

ג'נרוט תסריטי בדיקות מאפיון

תרגיל 1 - מאפיון טכני לתסריטים ב-ADO

תתרגלו עבודה עם Cursor Agent כבודקים ידניים: לצרף אפיון, לג'נרט תסריטים, לאתגר כיסוי, ולהפיק קובץ מוכן לייבוא ל-Azure DevOps. אין צורך לכתוב קוד אפליקציה.

איך עובדים

  1. פתחו ב-Cursor את תיקיית exercises/ai-for-testers (Open Folder).
  2. פתחו את חלונית ה-Agent (ברירת מחדל: Ctrl+I / Cmd+I).
  3. ודאו שאתם במצב Agent (ולא Ask בלבד).
  4. בצעו את השלבים לפי הסדר. לכל שלב: מטרה, שלבים, ו"מה למדנו".

שלב 0 - הכנה ב-Cursor

מטרה

לוודא שה-workspace נכון, שאתם ב-Agent mode, ושאתם יודעים לצרף קובץ לשיחה.

שלבים

  1. ב-Cursor: File → Open Folder ובחרו את תיקיית ai-for-testers.
  2. פתחו את fixtures/technical-spec.md ועיינו 2-3 דקות במבנה (AC, Business Rules, מקרי קצה).
  3. פתחו Agent. אם מופיע Ask/Chat בלבד, עברו ל-Agent.
  4. בדקו צירוף קובץ: גררו את האפיון לצ'אט, או השתמשו ב-@ ובחרו את הקובץ.
  5. בדיקת עשן קצרה:

    "קרא את fixtures/technical-spec.md. במשפט אחד: מה הפיצ'ר, ובמשפט שני: מה מחוץ להיקף?"

מה למדנו
  • לבודק, "סביבת פיתוח" = תיקייה + אפיון + Agent, לא בהכרח IDE של קוד.
  • צירוף קובץ מפורש מנצח הסתמכות על "המודל כבר יודע".

עברו ל-שלב 1 - ג'נרוט תסריטים.

שלב 1 נושא: פרומפט ראשון, שדות חובה ל-ADO.

שלב 1 - ג'נרוט ראשוני של תסריטי בדיקות

מטרה

לקבל רשימת Test Cases שמכסה את הלוגיקה העסקית באפיון, עם שדות שמתאימים לעבודה מול ADO.

שלבים

  1. ודאו ש-fixtures/technical-spec.md מצורף לשיחה.
  2. הריצו:

    "קרא את מסמך האפיון הטכני המצורף (fixtures/technical-spec.md). ג'נרט רשימת תסריטי בדיקות (Test Cases) המכסים את כל הלוגיקה העסקית ותנאי הקבלה. עבור כל תסריט כלול: Title, Description, Pre-Conditions, Steps, Expected Result, Priority (1-4), Automation Status (Manual), ומיפוי למזהי AC (למשל AC-03). אל תמציא יכולות מחוץ להיקף (SMS, המרת מטבע)."

  3. סקרו את התשובה הראשונה. סמנו לעצמכם מה נראה חזק ומה חסר. אל תמשיכו לייצוא עדיין.
רף איכות מינימלי לשלב זה

לפחות 8 תסריטים, וכל תסריט עם Steps מספריים (לא פסקה אחת). אם קיבלתם פחות, בקשו להרחיב לפני שלב 2.

מה למדנו
  • פרומפט טוב לבודק מגדיר פורמט שדות, לא רק "תכתוב טסטים".
  • הפלט הראשון הוא טיוטה לעבודה, לא תוצר סופי.

עברו ל-שלב 2 - אתגר כיסוי.

שלב 2 נושא: Iterative refinement, אתגר מקצועי.

שלב 2 - אתגר כיסוי (חובה לפני ייצוא)

מטרה

להוכיח שהרשימה מכסה Edge Cases, Negative Scenarios והרשאות. זה השלב שבו נוצר הערך האמיתי.

שלבים

  1. באותו session, שאלו:

    "אילו מקרי קצה (Edge Cases), תרחישי שליליים (Negative), ותרחישי הרשאות שמופיעים באפיון (במיוחד סעיף 7 ו-AC-07/AC-08) אינם מכוסים ברשימה שיצרת? הצג טבלת פערים: AC/BR מול תסריט קיים או חסר."

  2. בקשו השלמה:

    "השלם את התרחישים החסרים. חובה לכלול לפחות: (1) סף שווה ליתרה בדיוק, (2) סף לא חוקי <=0, (3) viewer מול owner, (4) כשל ב-balance API, (5) חשד לבאנר stale אחרי כיבוי התראה. עדכן את הרשימה המלאה."

  3. בדקו מול ה-Definition of Done שבאפיון:
    • כל AC-01..AC-12 ממופה לתסריט אחד לפחות
    • לפחות 4 תרחישי Negative/Edge מסעיף 7
    • תסריט הרשאות אחד לפחות
    • אין תסריטים מחוץ להיקף
  4. אם משהו חסר, המשיכו באותו session עד שהצ'קליסט ירוק.
אתגר בונוס

בקשו מה-agent לדרג את התסריטים לפי סיכון עסקי (לא רק Priority מספרי) ולהצביע על 3 תסריטים שחייבים לרוץ ב-smoke לפני שאר הסבב.

מה למדנו
  • תהליך מבוסס איטרציות: הבסיס בצעד 1, האיכות בצעד 2.
  • בודק מקצועי מאתגר כיסוי; הוא לא מאשר "נראה סבבה".

שלב 3 נושא: מטקסט לפורמט ארגוני.

שלב 3 - המרה לתבנית ייבוא ל-ADO

מטרה

להפוך את רשימת התסריטים לטבלה שמתאימה לייבוא Test Cases ב-Azure DevOps.

שלבים

  1. פתחו לעיון את fixtures/ado-import-template.csv (שימו לב: תסריט אחד = מספר שורות, שורה לכל Step).
  2. בקשו:

    "מנה את כל תסריטי הבדיקות שסיכמנו והצג אותם בטבלה לייצוא CSV לייבוא ל-Azure DevOps. שמות העמודות חייבים להיות בדיוק: Work Item Type, Title, Test Step, Step Action, Step Expected, Priority. Work Item Type = Test Case. כל Step בשורה נפרדת עם אותו Title. Priority מספרי. התאם לדוגמה ב-fixtures/ado-import-template.csv."

  3. ודאו שאין עמודות מיותרות ושצעדים ממוספרים עולים (1, 2, 3...).
מה למדנו
  • חיבור לפורמט ארגוני הופך תוצר AI מכלי שיחה לקובץ עבודה.
  • תבנית לדוגמה ב-context מפחיתה המצאות של שמות עמודות.

עברו ל-שלב 4 - ייצוא וייבוא.

שלב 4 נושא: CSV/Excel ו-ADO Import.

שלב 4 - ייצוא וייבוא ל-Azure DevOps

מטרה

להוציא קובץ נקי ולייבא (או לבצע dry-run) כך שהתסריטים קיימים במערכת.

שלבים

  1. בקשו מה-agent ליצור קובץ CSV בתיקייה, למשל:

    "שמור את טבלת הייבוא לקובץ output/low-balance-testcases.csv עם אותן עמודות, encoding שמתאים ל-Excel."

  2. פתחו ב-Excel / Google Sheets, ודאו יישור עמודות, ושמרו.
  3. אם יש גישת ADO בהדרכה:
    1. Azure DevOps → הפרויקט → Test Plans (או Import Work Items לפי מדיניות הארגון).
    2. Import Test Cases / Import, העלו את הקובץ.
    3. בצעו Mapping לשדות במידת הצורך, אשרו, וודאו שהתסריטים נוצרו.
  4. Dry-run (אם אין גישה): השוו ידנית את הקובץ שלכם ל-ado-import-template.csv. סמנו: אותן כותרות, Steps מפוצלים, אין תאים שבורים בפסיקים לא מוקלטים. זה מספיק לסיום השלב בהדרכה.
מה למדנו
  • ה-agent יכול לייצר את הקובץ; האחריות על תקינות הייבוא נשארת אצלכם.
  • Fallback מתוכנן מראש מונע תקיעת תרגיל כש-ADO חסום.

שלב 5 - סגירה ו-Review

צ'קליסט סגירה

  • כיסוי AC מלא לפי מיפוי שביצעתם

  • מה תיקחו איתכם לתרגיל 2 (מייל סטטוס)?

  • אתם ה-Reviewer: האחריות על כיסוי האפיון והדיוק ב-ADO נשארת אצל בודק התוכנה.

שלב 1

שלב 1 - חיבור Azure DevOps MCP

מטרה

לחבר את Cursor ל-ADO כדי שה-agent יוכל לשלוף באגים ותמונת סטטוס בלי copy-paste ידני.

MCP Setup

הכנת MCP: Azure DevOps

  1. החליפו את YOUR_ADO_ORG בשם הארגון מהמדריך.
  2. ב-Cursor: Settings → Tools & MCP → New MCP Server, או צרו/ערכו .cursor/mcp.json ב-workspace (או %USERPROFILE%\.cursor\mcp.json).
  3. הוסיפו:
{
  "mcpServers": {
    "ado": {
      "command": "npx",
      "args": ["-y", "@azure-devops/mcp", "YOUR_ADO_ORG"]
    }
  }
}
  1. שמרו, Reload ל-Cursor, אשרו Enable, וודאו נקודה ירוקה ליד ado.
  2. בדיקת עשן:

    "האם כלי Azure DevOps MCP זמינים? רשום בקצרה מה אתה יכול לעשות מול Work Items ו-Test Plans."

אבטחה: אל תשמרו PAT בתוך repo משותף. השתמשו במשתנה סביבה מקומי לפי הנחיות המדריך.

Fallback

אם MCP חסום: פתחו Query/Test Plan בדפדפן, העתיקו סיכומי ספירות + רשימת באגים קריטיים, והדביקו ל-Agent כהקשר ידני בהמשך.

מה למדנו
  • MCP מחבר את ה-agent למערכת הארגונית; זה ה-context האמיתי לדיווח.

מטרה

לאפשר יצירת טיוטת מייל בתיבה שלכם, בלי שליחה. אם החיבור לא זמין, נעבוד ב-Fallback מלא.

MCP Setup

הכנת MCP: Microsoft Outlook / Graph (Draft)

בסביבות ארגוניות החבילה וההרשאות משתנות. השתמשו בהגדרה שהמדריך מאשר. תבנית נפוצה לשרת MCP מבוסס Graph (דוגמה להמחשה):

{
  "mcpServers": {
    "ado": {
      "command": "npx",
      "args": ["-y", "@azure-devops/mcp", "YOUR_ADO_ORG"]
    },
    "outlook": {
      "command": "npx",
      "args": ["-y", "@microsoft/outlook-mcp"]
    }
  }
}

אם החבילה @microsoft/outlook-mcp אינה זמינה / נחסמת במדיניות הארגון: דלגו על Outlook MCP ועבדו ב-Fallback (שלב 4). אל תבזבזו את זמן התרגיל על התקנה שלא עוברת אישור אבטחה.

  1. אם השרת עלה: בדיקת עשן:

    "האם כלי Outlook MCP זמינים? אילו פעולות קיימות לגבי יצירת טיוטה? אשר שאין פעולת Send בשימוש בתרגיל הזה."

  2. כתבו לעצמכם כלל: בכל בקשה למייל תופיע המילה Draft בלבד / אל תשלח.

Fallback (מומלץ להכיר גם כשיש MCP)

ה-agent מייצר את גוף המייל המעוצב בצ'אט → אתם מעתיקים ל-Outlook ידנית כטיוטה → מוסיפים נמענים → שולחים רק אחרי Review.

מה למדנו
  • Human-in-the-loop: חיבור חי לנתונים כן; שליחה אוטומטית לא.
  • Fallback מתוכנן = תרגיל שלא נשבר על מדיניות IT.

שלב 3

שלב 3 - ניסוח פרומפט לדיווח סטטוס

מטרה

לבנות בקשה אחת מקיפה: MSP, TestPlan, תבנית איכות, וכללי בטיחות.

שלבים

  1. צרפו את fixtures/email-template.md לשיחה. במצב offline צרפו גם fixtures/demo-ado-status.md.
  2. השתמשו בערכי הדמו (או במה שכתב המדריך) והריצו:

    "צור מייל סטטוס בדיקות מעודכן עבור סבב הבדיקות הנוכחי ב-Azure DevOps.
    שם חבילת העבודה (MSP): MSP-FinDash-Q3
    שם תוכנית הבדיקות (TestPlan): TP-LowBalance-Alert
    שלוף נתונים עדכניים מ-ADO (MCP) לפי מיפוי השדות ב-fixtures/email-template.md. אם אין MCP או שהוא נכשל: השתמש רק בנתונים מ-fixtures/demo-ado-status.md ואל תמציא מספרים.
    עצב בדיוק לפי מבנה התבנית והדוגמה בקובץ.
    אם חסר נתון: כתוב במפורש 'לא זמין' ואל תמציא מספרים.
    תוצר: טיוטת Draft בלבד. אל תשלח מייל. אל תמלא נמענים."

למה הדוגמה חשובה

Few-Shot בתבנית מייצר סטנדרט אחיד לצוות הבדיקות וחוסך ויכוחים על מבנה בכל סוף יום.

מה למדנו
  • פרומפט סטטוס טוב = מזהי סבב + תבנית + איסור המצאה + איסור שליחה.

עברו ל-שלב 4 - טיוטת מייל.

שלב 4

שלב 4 - שליפת נתונים ויצירת טיוטה

מטרה

לאשר הרצות MCP, לקבל טיוטה (או גוף מייל), ולבדוק שהמספרים לא הומצאו.

שלבים

  1. אשרו לסוכן להריץ כלי ADO (שליפת Bugs / Test Plan לפי הזמין).
  2. עם Outlook MCP: אשרו רק יצירת Draft בתיבה שלכם. בדקו ב-Outlook שהטיוטה קיימת ושדה To ריק או לא נשלח.
  3. בלי Outlook MCP: העתיקו את גוף המייל מהצ'אט לטיוטה ידנית ב-Outlook.
  4. השוו 2-3 מספרים מול ADO בדפדפן (למשל ספירת Critical פתוחים). אם יש פער, תקנו בפרומפט הבא.
מה למדנו
  • הסוכן חזק כשהוא נסמך על tool results, לא על זיכרון מודל.
  • דגימת אימות ידנית קצרה מונעת דיווח מביך למנהלים.

עברו ל-שלב 5 - טיוב.

שלב 5

שלב 5 - Feedback Loop עד לתוצאה מיטבית

מטרה

לטייב את הטיוטה בדיאלוג עד שהסטטוס מדויק, חד, ומוכן להפצה ידנית.

שלבים

  1. סקרו את הטיוטה מול ה-checklist ב-email-template.md.
  2. בקשות טיוב לדוגמה (הריצו מה שרלוונטי):

    "הדגש בטבלה את הבאגים הקריטיים שנפתחו או עודכנו היום."

    "קצר את פסקת התקציר הניהולי ל-3 שורות, עם Blocker במשפט הראשון אם קיים."

    "הוסף התרעה מפורשת על חסימה (Blocker) בתרחיש X / BUG מספר Y."

  3. חזרו עד שאתם מוכנים להוסיף נמענים ידנית. עדיין בלי Send מה-agent.

Definition of Done לטיוטה

  • Subject בתבנית הנכונה
  • דשבורד התקדמות + Severity
  • Critical היום + Blockers מודגשים
  • אין מספרים מומצאים
  • Draft בלבד / ללא שליחה אוטומטית
מה למדנו
  • אוטומציה בטוחה = MCP לנתונים חיים + עצירה ב-Draft + Review אנושי.
  • אחידות בדיווח נוצרת מתבנית ודוגמת איכות, לא מכשרון חד-פעמי.

עברו ל-שלב 6 - שיפור יומיומי.

שלב 6

שלב 6 - שיפור יומיומי להצגה למנהלים

מטרה

לבחור משימת QA שחוזרת עליכם, ולתכנן איך Agent + context + כלים מקצרים אותה. זה החומר להצגות.

שלב א' - בחירת משימה

בחרו אחת (או הציעו דומה מהעבודה שלכם):

  • סיכום באגים חדשים מאמש לבוקר סטנדאפ
  • בניית מטריצת כיסוי מתוך אפיון / User Story
  • ניסוח Bug report איכותי מתצפיות גולמיות
  • הכנת Checklist לרגרסיה לפני Release

שלב ב' - מדידת "לפני"

  • כמה זמן זה לוקח היום?
  • מה משתנה באיכות בין בודקים?
  • איפה יש copy-paste או חיפוש ידני חוזר?

שלב ג' - תכנון עם Agent

"המשימה היומית שלי היא: [...]. עזור לי לעצב זרימת עבודה ב-Cursor: איזה context לצרף, האם צריך MCP, מה ה-Definition of Done, ואיפה חייב Review אנושי. אל תממש עדיין, רק תוכנית."

שלב ד' - "אחרי" והכנה למנהלים

  • מה התקצר / השתפר?
  • דמו של 2 דקות: לפני → אחרי
  • מסר אחד: agents עוזרים בעבודה היומיומית דרך context, משוב מכלים, ו-Review אנושי. לא טייס אוטומטי.
מה למדנו
  • הערך האמיתי הוא בשילוב בזרימת QA היומית, לא רק בתרגיל הכיתה.
  • שיפור קטן שחוזר כל יום מצטבר מהר יותר מ"וואו" חד-פעמי.
